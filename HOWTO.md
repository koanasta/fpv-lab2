# Як запустити все з нуля

Покрокова інструкція: від закритого терміналу до виконаного польоту.

---

## Крок 0. Відкрити термінал Ubuntu

Натисни **Пуск** → набери `Ubuntu` → відкрий застосунок **Ubuntu**.
Або відкрий **Windows Terminal** і в ньому натисни стрілку `⌄` біля плюса →
вибери **Ubuntu**.

Відкриється чорне вікно з рядком виду:

```
kobri@DESKTOP:~$
```

Це і є термінал Linux. Усі команди нижче вводяться саме тут.

> Знак `~` означає домашню теку `/home/kobri`. Проєкт лежить у `~/fpv_labs`.

---

## Крок 1. Прибрати за попереднім запуском

```bash
~/fpv_labs/scripts/stop_sim.sh
```

Має вивести `All simulation processes stopped, ports are free.`

Цей крок обов'язковий: якщо від минулого разу лишився процес Gazebo або
ArduPilot, він тримає мережевий порт 5760, і новий запуск впаде з помилкою
`bind failed on port 5760 - Address already in use`.

---

## Крок 2. Запустити симуляційне середовище

**Термінал 1:**

```bash
~/fpv_labs/scripts/start_sim.sh
```

Одна ця команда піднімає одразу чотири компоненти:

| Компонент | Роль |
|---|---|
| Gazebo Sim | фізика, світ `maze`, модель дрона |
| ArduPilot SITL | програмна модель польотного контролера |
| micro-ROS DDS-агент | міст між ArduPilot і ROS 2 |
| RViz | візуалізація даних ROS 2 |

У терміналі побіжить довгий лог — **це нормально, так і має бути**.
**Не закривай цей термінал і не натискай Ctrl+C** — поки він відкритий,
симуляція живе.

За 10–20 секунд з'явиться вікно **Gazebo Sim** із сірим лабіринтом.

---

## Крок 3. Відкрити другий термінал

Симуляція займає перший термінал, тому політ запускається з окремого.

У Windows Terminal натисни **`+`** (новий таб) → **Ubuntu**.
Або ще раз відкрий застосунок **Ubuntu** з Пуску.

---

## Крок 4. Запустити політ

**Термінал 2** — власний алгоритм, варіант 8:

```bash
~/fpv_labs/scripts/run_goto_point.sh 4.6 1.4
```

Спершу скрипт напише `Waiting for the vehicle to become armable...` і
почекає 1–2 хвилини. Це не зависання: автопілоту потрібен час, щоб фільтр
EKF збігся на розв'язку GPS. Поки цього не сталося, ArduPilot відмовляється
вмикати двигуни.

Далі побачиш послідовність:

```
Pre-arm check passed: Vehicle is Armable     перевірка готовності пройдена
GUIDED mode enabled                          режим керованого польоту
Motors armed                                 двигуни озброєно
Requesting takeoff to 2.0 m                  зліт
Take-off altitude reached: 1.83 m            висота набрана
Hover stabilised, starting flight...         починається політ до цілі
x=1.77 y=0.53 | distance 2.96 m | speed 1.50 m/s
x=3.87 y=1.17 | distance 0.77 m | speed 0.46 m/s     ← гальмування
Target reached, distance 0.233 m
----- RESULT -----                           ← ОСЬ ЦЕ ПОТРІБНО ДЛЯ ЗВІТУ
Start position:  x=0.000 y=0.000
Target position: x=4.600 y=1.400
Actual position: x=4.488 y=1.366 z=2.191
Position error:  e=0.117 m
------------------
LAND mode enabled                            посадка
Landing completed
Flight test completed successfully
```

Увесь політ триває 2–4 хвилини: симуляція йде втричі-вчетверо повільніше за
реальний час.

Журнал зберігається автоматично в `~/fpv_labs/logs/`.

Щоб запустити приклад викладача замість власного алгоритму:

```bash
~/fpv_labs/scripts/run_flight_test.sh
```

---

## Крок 5. Скріншоти для звіту

Потрібні два: дрон на початку маршруту і в кінцевій точці.

1. `Alt+Tab` → вікно **Gazebo Sim**
2. У панелі **Entity tree** справа знайди **`iris`** — це дрон
3. Правий клік на `iris` → **Move to** — камера перелетить до дрона
4. Колесом миші трохи відсунься, щоб у кадр потрапили стіни лабіринту
5. `Win+Shift+S` → виділи вікно Gazebo → `Ctrl+V` у Word

**Знімок 1** роби до запуску польоту (дрон на землі в точці 0,0).
**Знімок 2** — коли в терміналі з'явиться `----- RESULT -----`.

Керування камерою: ліва кнопка + рух = обертати, колесо = наближення,
середня кнопка + рух = зсув.

---

## Крок 6. Завершити

У **терміналі 1** натисни `Ctrl+C`, потім:

```bash
~/fpv_labs/scripts/stop_sim.sh
```

---

## Якщо щось пішло не так

| Що бачиш | Що зробити |
|---|---|
| `bind failed on port 5760` | `~/fpv_labs/scripts/stop_sim.sh`, потім запустити знову |
| `Vehicle is not armable` | почекати ще; якщо понад 5 хв — перезапустити середовище |
| Вікно Gazebo не з'явилось | глянути в терміналі 1, чи немає рядків `[ERROR]` |
| Дрон стартує не з (0,0) | перезапустити середовище: він стартує з місця попередньої посадки |
| Команда `не знайдена` | перевірити шлях: має бути саме `~/fpv_labs/scripts/...` |

## Що показати й розповісти викладачу

### 1. Середовище (Завдання 1)

Показати вікно Gazebo з моделлю дрона і вивід:

```bash
source ~/fpv_labs/scripts/setup_env.sh
ros2 topic list | grep /ap/
ros2 service list | grep /ap/
```

Це доводить, що ROS 2 бачить теми та сервіси ArduPilot: `/ap/v1/status`,
`/ap/v1/cmd_vel`, `/ap/v1/arm_motors`, `/ap/v1/mode_switch`,
`/ap/v1/prearm_check`, `/ap/v1/experimental/takeoff`.

**Про версії.** У методичці вказано ROS 2 Humble і шлях
`/opt/ros/humble/setup.bash`, у роботі використано **Jazzy**. Причина:
Humble випускається лише для Ubuntu 22.04 і на Ubuntu 24.04 не
встановлюється; відповідним LTS-випуском для 24.04 є Jazzy, парна до нього
версія Gazebo — Harmonic. Методичка це припускає: «конкретні шляхи можуть
відрізнятися залежно від способу встановлення».

### 2. Скрипти автоматизації (Завдання 2)

Показати `~/fpv_labs/scripts/` — шість скриптів. Ключова теза: запуск
чотирьох компонентів зведено до однієї команди, а `stop_sim.sh` вирішує
проблему з таблиці 2.2 методички («повторний запуск не працює») — він не
просто вбиває процеси, а чекає фактичного звільнення портів.

### 3. Приклад викладача (Завдання 3)

`run_flight_test.sh` — зліт, зависання 30 с, посадка.

### 4. Власний алгоритм (Завдання 4)

Головна теза: **базові класи не змінювалися**. `GotoPointNode` успадковано
від `FlightTestNode`, вісім базових обробників станів узято як є, замінено
лише обробник стану `HOVERING` і додано два нові стани — `GOING_TO_TARGET`
і `STOPPING`.

Закон керування — пропорційний з гальмуванням:

```
v = max(min_speed, max_speed * min(1, d / slowdown_radius))
```

Далеко від цілі дрон летить 1,5 м/с; у межах 2,5 м швидкість спадає
пропорційно відстані. Це прямо відповідає пункту 8 Завдання 4
(«зменшувати швидкість під час наближення до цілі»).

Команди йдуть у тему `/ap/v1/cmd_vel` повідомленням `TwistStamped` з
`frame_id = "map"`, положення читається з `/odometry`.

### 5. Результат (Завдання 5)

| Показник | Значення |
|---|---|
| Початкове положення | x₀ = 0,000; y₀ = 0,000 |
| Задані координати цілі | x = 4,600; y = 1,400 |
| Фактичні координати | x = 4,488; y = 1,366 |
| Похибка | **e = 0,117 м** |

Проти рекомендованих методичкою 0,2–0,3 м.

### 6. Питання, яке варто поставити викладачу

Додаток 2 задає ціль як `x_target = x0 − Δx` і водночас стверджує, що у
світі `maze.sdf` прямі маршрути не перетинають стін. Ці дві умови
суперечать одна одній: у буквальному трактуванні маршрут упирається в стіну
`Wall_9` (вона проходить по `x = −1` від `y = −1` до `y = 7`) в **усіх 56**
варіантах таблиці 2.3. Це підтверджено експериментально — дрон дійшов до
`x = −0,79` і ArduPilot видав `Crash: Disarming: AngErr=37>30`.

У протилежному напрямку всі 56 маршрутів вільні із запасом понад 0,6 м, що
відповідає твердженню методички. Тому напрямок винесено в параметр
`axis_direction`: за замовчуванням `+1` (робочий), значення `-1` виконує
формулу буквально.

Питання до викладача: у якій системі координат задаються `x0`, `y0` —
можливо, малася на увазі не та, у якій публікується тема `/odometry`.
