# Лабораторна робота №2 — моделювання БПЛА в Gazebo та ArduPilot SITL

Моделювання безпілотної авіаційної системи на базі **Gazebo Sim**,
**ArduPilot SITL** і **ROS 2**: запуск симуляційного середовища, виконання
наданого прикладу польоту та власний алгоритм польоту до заданої точки з
автоматичною посадкою.

**Варіант 8:** Δx = 4,6 м; Δy = 1,4 м.

## Середовище

| Компонент | Версія |
|---|---|
| ОС | Ubuntu 24.04.5 LTS (Noble), x86_64, WSL 2 на Windows 11 |
| ROS 2 | Jazzy Jalisco |
| Gazebo Sim | Harmonic 8.15.0 |
| ArduPilot | ArduPilot-4.6.0-beta1-8542-g14c871f273 |
| Python | 3.12.3 |

ROS 2 Humble не використовується, оскільки не випускається для Ubuntu 24.04;
відповідним LTS-випуском є Jazzy, парна до нього версія Gazebo — Harmonic.

Повна інструкція розгортання, перелік виявлених і усунених проблем та опис
алгоритму — у файлі [DEPLOY.md](DEPLOY.md).

## Структура

```
fpv_labs/
├── DEPLOY.md                     інструкція розгортання та опис алгоритму
├── scripts/                      скрипти швидкого запуску (Завдання 2)
│   ├── setup_env.sh              спільне середовище ROS 2 / ardu_ws / fpv_labs
│   ├── start_sim.sh              Gazebo + ArduPilot SITL + DDS-агент + RViz
│   ├── stop_sim.sh               зупинка процесів і звільнення портів
│   ├── wait_ready.sh             очікування готовності автопілота (pre-arm)
│   ├── run_flight_test.sh        Завдання 3 — приклад викладача
│   └── run_goto_point.sh         Завдання 4 — політ до заданої точки
└── src/fpv_lab2/
    └── fpv_lab2/
        ├── flight_test/          наданий приклад (зліт, зависання, посадка)
        │   ├── flight_state.py
        │   ├── flight_test_node.py
        │   ├── main.py
        │   └── handlers/         8 обробників станів
        └── goto_point/           власний алгоритм польоту до точки
            ├── goto_state.py     додаткові стани
            ├── goto_point_node.py
            ├── main.py
            └── handlers/         стабілізація, наведення, зупинка
```

Модуль `goto_point` **перевикористовує базові класи прикладу без змін**:
`GotoPointNode` успадковано від `FlightTestNode`, вісім базових обробників
станів узято як є, замінено лише обробник стану `HOVERING` і додано два нові
стани — `GOING_TO_TARGET` і `STOPPING`.

## Запуск

Термінал 1 — симуляційне середовище:

```bash
~/fpv_labs/scripts/start_sim.sh
```

Термінал 2 — приклад викладача (Завдання 3):

```bash
~/fpv_labs/scripts/run_flight_test.sh
```

Термінал 2 — власний алгоритм (Завдання 4):

```bash
~/fpv_labs/scripts/run_goto_point.sh 4.6 1.4
```

Зупинка середовища:

```bash
~/fpv_labs/scripts/stop_sim.sh
```

## Результат

| Показник | Значення |
|---|---|
| Початкове положення | x₀ = 0,000 м; y₀ = 0,000 м |
| Задані координати цілі | x = 4,600 м; y = 1,400 м |
| Фактичні координати перед посадкою | x = 4,488 м; y = 1,366 м; z = 2,191 м |
| Похибка позиціонування | **e = 0,117 м** |
| Довжина маршруту | 4,81 м |
| Посадка | виконана автоматично, кінцева висота 0,19 м |

Похибка обчислена за формулою методички:

```
e = sqrt((4,488 - 4,600)^2 + (1,366 - 1,400)^2) = 0,117 м
```

Значення укладається в рекомендовані методичкою 0,2–0,3 м.
Журнал виконання — у каталозі [logs/](logs/).

## Примітка щодо напрямку зміщення цілі

Додаток 2 методички задає ціль як `x_target = x0 - Δx` і водночас стверджує,
що у світі `maze.sdf` прямі маршрути від старту до заданих точок не
перетинають стін. Перевірка геометрії світу показала, що ці дві умови
суперечать одна одній: у буквальному трактуванні маршрут упирається в стіну
`Wall_9` (x = -1) в усіх 56 варіантах таблиці 2.3, тоді як у протилежному
напрямку всі 56 маршрутів вільні. Тому напрямок винесено в параметр
`axis_direction` (детальніше — розділ 6 у [DEPLOY.md](DEPLOY.md)).
